Scalewing request from Teisoro.

Status: accepted 2026-10-19 (Teisoro F-014-S03 "Scalewing: file picker, PDF viewer, Markdown view, blue count", task 2610; the training library inventory's rows 15 and 19 and §2; the training documents contract §7; plan approval under the owner's F-014 delegation of 2026-10-19).
Renderer: react
Missing surface: `MarkdownView`, a safe subset of Markdown drawn in Scalewing's type, and `inspectMarkdown`, what it shows in headings and what it leaves out.
Why Box/Stack/Inline/Card/Text/Button/Field cannot do this: managers write or paste training pages in Markdown (Teisoro keeps the text as written, up to 50,000 characters a language). The page reader draws paragraphs, headings, lists, bold, italic, links, photos with captions and a highlighted box in the app's type, with "On this page" built from the headings; the editor shows a live preview and lists what will not be shown before saving. Drawing that needs a Markdown parser and a renderer that can never turn the text into HTML, scripts, outside images or `javascript:` links.
Existing surface this might already be: `Text` (one run of words, no structure); `dangerouslySetInnerHTML` with a Markdown-to-HTML library and a sanitizer (HTML from a string, which the contract forbids, and the sanitizer's rules would be Teisoro's to keep right).
Workaround I almost used: a Teisoro composite over a Markdown library, with its own CSS, which Teisoro does not write.
Teisoro use: the page reader (desktop and phone), the page editor's live preview and its "left out" notice, the "On this page" list (S05).
Proposed API (inventory): `MarkdownView` (§7 of the contract's subset, headings with ids, photos with captions, the highlighted box; reports what it left out).

## Accepted API (2026-10-19)

- `MarkdownView` (`MarkdownViewProps`):
  - `source: string`, the Markdown as written or pasted;
  - `resolveImage?: (id: string) => { src: string; alt?: string } | null`, the consumer's photos by id (`MarkdownImageResolver`, `MarkdownImage`), kept stable (`useCallback`) since a new function reads the source again;
  - `idPrefix?: string`, put before every heading id (empty, the default, or a letter first, then letters, digits, `-` or `_`); every view on a page takes its own, or its ids can clash with the page's;
  - `newTabLabel: string` (required, product copy), hidden words after every link ("(opens in a new tab)").
- `inspectMarkdown(source, { resolveImage?, idPrefix? })` returns a `MarkdownInspection`: `headings` (`MarkdownHeading`: `id`, `level` 1 to 3, `text`) with the ids the view gives; `omissions`, the first 100 `MarkdownOmission`s (`kind`: `html`, `table`, `image`, `link`, `code` or `limit`, listed in `markdownOmissionKinds`; `source`, the left-out text cut to 80 characters with "…"); and `omissionCounts`, how many of each kind, past the first 100 too. Pure; it refuses what the view refuses, the same way, and the same options give the same answer.
- What it draws, as React elements (never `dangerouslySetInnerHTML`, never HTML from a string):
  - paragraphs, with hard line breaks;
  - headings: `#` as an `h2` (the page has its own title), `##` an `h3`, `###` and deeper an `h4`, at the title, body and label sizes and the title's weight; each with an id from its words (NFKD letters and digits, lower case, joined by `-`; "section" when it has none; repeats get `-2`, `-3`);
  - bullet and numbered lists (a numbered list keeps its start), nested, tight or loose;
  - bold and italic;
  - links, only when the address read as the browser reads it (`new URL`, so tabs, newlines and character references are decoded first) is `http:`, `https:` or `mailto:`; they open in a new tab with `rel="noopener noreferrer"`, in the accent colour and underlined;
  - block quotes as the highlighted box: the accent's subtle tint, an accent bar at its start, the small radius; a link (still underlined) and a photo caption in it are the text colour (neither the accent nor the muted colour clears 4.5:1 on the tint in every palette);
  - thematic breaks as a `Separator`;
  - photos: `![caption](photo:<id>)` (the id letters, digits, `-` and `_`, up to 64), resolved by the consumer, drawn as a figure at the page's width (the medium radius) with the caption muted under it, never inside a paragraph (a paragraph is split around it; a dropped image leaves it whole with one space). The image's `alt` is the resolver's, else the caption, so a photo is never announced as decorative (a screen reader then reads the caption twice, which the review accepted over an image with no words); a photo with neither has no words and is left out. Its `src` must be relative, `https:`, `http:`, `blob:` or a `data:image/` PNG, JPEG, GIF, WebP, AVIF or SVG (an `img` never runs an SVG's script); any other is left out.
- What it leaves out, and reports:
  - raw HTML, inline or as a block, scripts included (`html`); a tag's words between tags stay;
  - tables (`table`), recognised with the GFM table syntax so they are left out whole, not shown as pipes;
  - any other image: an outside address, `data:`, an unknown or malformed `photo:` id, an image inside a link, a mark or a heading, every image when there is no resolver (`image`);
  - a link or autolink with any other scheme (`javascript:`, `data:`, `vbscript:`, `file:`, `ftp:`, `tel:`), a relative or protocol-relative address, or an address that is not a URL; reference links whose definition is one of those (`link`); the link's words stay as plain text;
  - code: inline code and code blocks are shown as plain text, a block's lines kept, with no highlighting (`code`);
  - limits (`limit`): quotes, lists and marks nested past 16 levels are shown as their words (any HTML, table or image in them still left out and reported as such); a link there is drawn as its words and quoted in the run's one omission as `[words](address)`; the parser reads 128 levels deep (a quote is one level, a list and its item two, so 60-deep lists read whole), and a block reaching its last level, past which it stops reading, is reported once as it may be lost.
- Unknown tokens: the parser reads only CommonMark and GFM tables (no strikethrough, footnotes or bare-URL links); any other token's words stay as text, and nothing is drawn from a token the readers do not name.
- A `source` that is not text, a bad `idPrefix` or a `resolveImage` that is not a function throws a `RangeError` in the view and in `inspectMarkdown`; a blank or missing `newTabLabel` throws in the view.
- Bounded parsing: markdown-it's work is linear in the text. Its nesting cap (128) bounds blocks and its inline rules, and its work on runs of link and image openers grows with that cap (25,000 `![` took 1.2 s at 1,000 levels, 0.1 s at 128); emphasis can still nest deeper (8,333 levels at 50,000 characters), so the reader opens no frame past 16 levels and places each word once, keeping the reading linear at any depth. A first version on `mdast-util-from-markdown` (micromark) was dropped in review: micromark's work for each quote, list item, setext heading and lazy line grows with the text it is parsing, so crafted pages took seconds to minutes (50,000 characters of `- - - …` took 388 s), and bounding it by rewriting the source or parsing in parts changed what pages meant.
- Reading time (Vitest in Node on the development Mac, idle), for crafted 50,000-character pages (nested and alternating quotes and lists, lazy lines, setext headings, sub-lists, rules, emphasis nested 8,333 deep in a paragraph, quote, heading or link, asterisk, underscore, bracket, link-opener, image-opener and backslash runs, nested links, wide tables, 60-deep lists, 10,000 headings, 5,500 HTML tags): 60 such pages read in 0 to 107 ms each (median 12 ms, nine in ten under 35 ms); the slowest is a run of 25,000 image openers (`![`). A realistic 50,000-character page reads in about 7 ms. `markdown-view.test.tsx` reads 36 of these pages with a bound set by how long a plain 50,000-character page takes at that moment (at least 2 s), room for a busy machine.
- Line endings `\r\n` and `\r` are read as `\n` (the parser's own rule).
- New exports `MarkdownView`, `MarkdownViewProps`, `MarkdownOptions`, `inspectMarkdown`, `MarkdownInspection`, `MarkdownHeading`, `MarkdownImage`, `MarkdownImageResolver`, `MarkdownOmission`, `MarkdownOmissionKind`, `MarkdownOmissionCounts`, `markdownOmissionKinds`. New classes `sw-markdown`, `sw-markdown-paragraph`, `sw-markdown-heading`, `-heading-1` to `-heading-3`, `sw-markdown-list`, `sw-markdown-item-text`, `sw-markdown-link`, `sw-markdown-quote`, `sw-markdown-figure`, `sw-markdown-image`, `sw-markdown-caption`. No new tokens or layers.

## New production dependencies (AGENTS.md rule 14)

- `markdown-it` 14.3.2 (MIT, published 2026-09-12), pinned exactly. A CommonMark parser to a token stream, with GFM tables built in. The view walks the tokens and draws only the kinds above; its HTML renderer is never called, so no HTML string is ever made. Raw HTML is read as HTML tokens (left out), every link is read as a link so the view decides on its address (`safeLinkHref`), and bare-URL linking is off. Its work is linear in the text and its nesting is capped, which matters because Teisoro shows one manager's text to every reader. It brings `entities`, `mdurl`, `uc.micro`, `punycode.js` and `linkify-it` (MIT, the same maintainers), and `argparse` (Python-2.0, a permissive licence) for its command line, which the browser never loads.
- Weight: about 149 kB minified, 53 kB gzip (esbuild, browser build), mostly its HTML entity table and Unicode data; none of it loads for an app that does not import `MarkdownView` or `inspectMarkdown` (the package marks only its CSS as having side effects, so bundlers drop the parser when it is unused). `@types/markdown-it` 14.2.0 is a development dependency; no public declaration names its types.
- Alternatives set aside: `mdast-util-from-markdown` (micromark), tried first, for the reason above; `marked` is built around HTML output; `react-markdown` brings `remark`/`rehype` (micromark again) and its own component mapping; a hand-written parser would get CommonMark's edge cases (nesting, references, autolinks, entities) wrong, and those are exactly where unsafe links hide.

### Differences from the boards (Teisoro D-2)

- The highlighted box is the palette's accent tint with an accent bar (the Procedure board's teal is that board's accent).
- Headings in the body are an `h2` to `h4` (the boards draw sizes, not levels): the page's own title is the `h1`. A `#` followed straight by `###` skips a level as written (axe's heading-order is a best practice, not a failure).
- Heading ids keep ASCII letters and digits only, so a heading in a non-Latin script is `section`, `section-2`; Teisoro's pages are English and Spanish, whose accents are dropped (`después` is `despues`).

### Known palette gap

- Links are the accent; in the harvest palette's dark scheme it is 4.24:1 on the surface, a gap the tokens tests already record (table rows and the ledger note it too). Teisoro uses `sky`, where links clear 4.5:1.
